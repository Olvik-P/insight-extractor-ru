# insight-extractor-ru

Пайплайн анализа **уже обезличенных** текстовых транскриптов B2B-звонков (менеджер / клиент) на русском языке: чанкинг с перекрытием → LLM-оценка по scorecard с привязкой к исходному тексту (evidence-by-reference) → валидация и агрегация в единый JSON-отчёт по звонку.

**Статус**: реализовано, покрыто тестами (41 pytest), живо протестировано на реальном DeepSeek API. Первое архитектурное изменение — `add-transcript-analysis-pipeline` — оформлено и заархивировано через OpenSpec (локальная папка `openspec/` с полной записью решений и требований — рабочий артефакт разработки, не публикуется в этом репозитории).

Проект начинался с русскоязычного дизайн-документа (`project.md`), позже удалённого из репозитория как устаревший — часть его идей была пересмотрена в ходе реализации (подробности — в локальном `CLAUDE.md`, тоже не публикуется).

## Возможности

- **Чанкинг с перекрытием** — транскрипт режется на пересекающиеся окна реплик (по умолчанию size=4, overlap=2), чтобы LLM не теряла точность на середине длинного диалога.
- **Evidence-by-reference вместо копирования цитат** — модель не пересказывает цитату своими словами, а указывает номер реплики (`turn_index`); сам текст система извлекает сама из исходного транскрипта. Это убирает целый класс галлюцинаций/искажённых цитат — сверять с fuzzy-match просто нечего, копии текста не существует.
- **PII-безопасность по умолчанию** — вход уже анонимизирован (токены вида `<ORG_A1B2C3D4>`, проставленные сторонним проектом [`Custom_NER`](../Custom_NER)); токены никогда не восстанавливаются обратно и всегда остаются как есть в выводе — у этого проекта физически нет доступа к оригинальным значениям.
- **Провайдер-агностичные LLM-адаптеры** — DeepSeek (основной), YandexGPT, GigaChat за одним интерфейсом (`LLMAdapter`). Structured output / function calling — первый путь, `json_object` + Pydantic-валидация + один повтор с фидбеком об ошибке — надёжный fallback.
- **Map-Rerank для критериев, Reduce для summary** — два разных способа мерджа чанков, подобранных под форму задачи: для критериев побеждает чанк с наибольшим числом подтверждённых evidence-реплик (confidence — только тай-брейк), для `summary` (боль клиента, возражения, action items) — объединение по всем чанкам с дедупликацией, а не выбор одного "лучшего".
- **Детерминированный `talk_ratio`** — соотношение речи менеджер/клиент считается кодом по длине реплик, не LLM-суждением.
- **Нормализация тегов** — лёгкий, не требующий ML-зависимостей эмбеддинг (хэш символьных n-грамм) + косинусная близость для схлопывания дублей вроде "дорого"/"слишком дорого".
- **CLI** — `python -m insight_extractor_ru.cli.main <transcript.json> --provider deepseek`.

## Архитектура

```
insight_extractor_ru/
├── core/              # Pydantic-контракты + оркестратор run_pipeline
├── preprocessing/     # чанкинг, рендер реплик с метками ролей
├── analysis/          # scorecard, промпт-шаблон, оркестрация анализа чанка
├── validation/        # резолвинг evidence (turn_index → текст), порог confidence/manual review
├── aggregation/       # Map-Rerank, Reduce, нормализация тегов, overall_score, talk_ratio
├── integrations/llm/  # адаптеры DeepSeek / YandexGPT / GigaChat + общий retry/fallback
├── utils/             # лёгкие эмбеддинги для нормализации тегов
├── cli/               # точка входа insight-extractor-ru
└── tests/             # 41 pytest-тест
```

```
транскрипт (уже анонимизирован)
    │
    ▼
[preprocessing] ──► пересекающиеся чанки реплик
    │
    ▼
[analysis] ──► LLM-вызов на чанк, evidence как ссылка на turn_index (не копия текста)
    │
    ▼
[validation] ──► резолвинг turn_index → реальный текст; confidence < 0.6 → на ручную проверку
    │
    ▼
[aggregation] ──► Map-Rerank (критерии) + Reduce (summary) → overall_score
```

## Установка

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -e ".[dev]"
```

## Настройка LLM-провайдера

Создайте `.env` в корне проекта (см. [.env.example](.env.example)):

```
DEEPSEEK_API_KEY=ваш_ключ
```

Для альтернативных провайдеров — `YANDEXGPT_API_KEY` или `GIGACHAT_ACCESS_TOKEN` (для GigaChat нужен уже полученный OAuth access token — обмен ключа авторизации на токен в этом проекте не реализован).

## Использование

```bash
python -m insight_extractor_ru.cli.main examples/transcripts/01_price_objection_with_competitor.json --provider deepseek --output result.json
```

Вход — JSON с уже обезличенным транскриптом:

```json
{
  "call_id": "sample-call-001",
  "turns": [
    {"turn_index": 1, "role": "manager", "text": "Расскажите про задачу"},
    {"turn_index": 2, "role": "client", "text": "Заявки теряются"}
  ]
}
```

Выход — `CallAnalysis`: `call_id`, `overall_score`, `criteria[]` (с `resolved_evidence[]`, `confidence`, `flags`), `summary` (`client_pain`, `objections`, `action_items`), `flags[]`. Полные примеры реальных прогонов — в [examples/transcripts/*.result.json](examples/transcripts/).

## Scorecard

| Критерий | Вес | Как считается |
|---|---|---|
| `discovery_depth` | 22% | LLM |
| `objection_handling` | 20% | LLM |
| `next_step_clarity` | 18% | LLM |
| `budget_qualification` | 14% | LLM |
| `tone_empathy` | 14% | LLM |
| `talk_ratio` | 12% | детерминированно, по длине реплик — не LLM |

`overall_score` — взвешенная сумма по критериям, не отправленным на ручную проверку (confidence ≥ 0.6).

## Тестирование

**Юнит-тесты** (41, `pytest insight_extractor_ru`): чанкинг и его границы, контракт LLM-адаптеров (HTTP замокан — без реальных запросов), оркестрация анализа чанка, резолвинг evidence и порог ручной проверки, Map-Rerank/Reduce мердж, нормализация тегов, `overall_score`, полный e2e-прогон оркестратора и CLI на заглушках.

**Живое тестирование** (`examples/`): 6 вручную написанных B2B-диалогов в [examples/transcripts/](examples/transcripts/), каждый с файлом `*.expected.json` — фактами, заложенными в диалог заранее, до всякого запуска модели (боль клиента, ожидаемое возражение, срок next step, грубый диапазон итогового балла). Сверка — [examples/check_expected.py](examples/check_expected.py).

**Важная оговорка**: это smoke-тест по собственноручно написанным ожиданиям для собственноручно написанных диалогов, а **не измерение реальной точности скоринга**. Настоящая точность требует реальных звонков с независимой человеческой разметкой — такого датасета в проекте нет.

При живом тестировании против DeepSeek было найдено и исправлено 5 реальных проблем (подробное обоснование каждой — в докстрингах соответствующего кода):
1. Модель DeepSeek V4 по умолчанию в режиме "thinking", который не совместим с принудительным `tool_choice` — требуется явно отключать.
2. `deepseek-chat` — устаревшая модель (снята с эксплуатации 24.07.2026), актуальная — `deepseek-flash`.
3. Модель иногда возвращает `evidence` как список голых чисел вместо списка объектов `{turn_index}` — добавлена терпимая к обеим формам валидация.
4. `httpx.Client()` по умолчанию использует 5-секундный таймаут — недостаточно для реальной генерации LLM, приводило к спорадическим сбоям.
5. Map-Rerank по одному confidence мог выбрать чанк с неполным контекстом — теперь сначала ранжирует по числу подтверждённых evidence-реплик.

## Плюсы

- Приватность обеспечена архитектурно, а не дисциплиной: PII-токены физически невозможно восстановить на этой стороне.
- Цитаты в выводе гарантированно реальны (evidence-by-reference), а не то, что модель могла придумать.
- Провайдер меняется без изменений в `validation`/`aggregation`.
- Реально протестировано против живого API, а не только моками — найдены и исправлены настоящие баги до того, как что-то было объявлено готовым.
- Минимум зависимостей для MVP — не требует векторной БД или тяжёлых ML-моделей.

## Минусы и известные ограничения

- Нормализация тегов ловит только лексические почти-дубликаты (общие подстроки); настоящие перефразировки без общих слов не схлопнутся — сознательный выбор для v1, не будет исправлено без запроса.
- Нет персистентного хранилища/дашборда (SQL-агрегация из исходного дизайн-документа не реализована).
- Нет семантического поиска по архиву звонков (RAG) — отложено до появления реальной потребности.
- Веса и состав scorecard — первый черновик, не откалиброван на реальных человеческих оценках.
- Живое тестирование — только на 6 вручную написанных диалогах, это не бенчмарк точности.
- Map-Rerank в теории всё ещё может выбрать менее информированный чанк, если evidence разнесены дальше, чем окно перекрытия чанков.
- GigaChat-адаптер требует уже полученный OAuth-токен — обновление токена не реализовано.
- Порог confidence и параметры чанкинга настраиваемые, но текущие значения по умолчанию не откалиброваны на реальных данных.
